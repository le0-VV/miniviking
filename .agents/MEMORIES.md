# Project Memory

- Project name: `miniviking`.
- Purpose: tiny local MLX runtime for OpenViking that hosts an LLM, an embedding model, or both.
- It must integrate out of the box with a stock OpenViking install by matching the server input/output that OpenViking expects.
- It should be installable with a macOS LaunchAgent so the MLX server starts with macOS and eagerly loads configured models at startup instead of loading them just-in-time on first request.
- Installer should detect host unified memory and choose defaults:
  - 8 GB unified memory: embedding `mlx-community/embeddinggemma-300m-4bit`; local LLM disabled by default so install should not download or start an LLM unless the user explicitly opts in.
  - 12 GB to 16 GB unified memory: embedding `mlx-community/embeddinggemma-300m-8bit`, LLM `mlx-community/gemma-4-e2b-it-4bit`.
  - More than 16 GB unified memory: embedding `mlx-community/embeddinggemma-300m-bf16`, LLM `mlx-community/gemma-4-e4b-it-4bit`.
- LLM inference should enforce JSON structured responses, use a reliability-focused system prompt, and use low or zero temperature for consistency.
- Remaining runtime configuration for both LLM and embeddings should balance performance, accuracy, and low memory usage, with settings adjusted by system memory budget and discussed before implementation.
- Confirmed decisions:
  - Server should expose OpenAI-compatible endpoints by default.
  - Install should use a per-user macOS LaunchAgent by default.
  - CLI should include `install`, `uninstall`, `start`, `stop`, `restart`, `status`, and `serve`.
  - Model downloads should happen during install and fail fast if unavailable.
  - Default bind should be `127.0.0.1:8745`, and the port must be customizable.
  - Priority order: OpenViking compatibility with next to no extra config, then safe memory usage, then performance.
  - Context-window sizing should be chosen after verification; memory ingestion likely does not need the full 128k context even if the selected LLMs support it.
  - Do not leave testing-only code paths or artifacts in release binaries; diagnostics should remain explicit developer/operator commands and not affect production serving behavior.
  - Packaging should produce a single `miniviking` binary that runs three explicit processes: `miniviking-server` for OpenAI-compatible HTTP/API orchestration and non-model duties, `miniviking-llm` for LLM inference, and `miniviking-embed` for embedding inference.
  - Distribution should include a Homebrew formula/tap path that builds Miniviking from source; do not rely on prebuilt release binaries.
  - The Homebrew install path should avoid Python virtualenv creation in the formula. If Python packaging is too brittle inside Homebrew, use a Rust-built binary/launcher and move Python/MLX runtime setup out of the formula build.
  - Because this repository is named `miniviking` rather than `homebrew-miniviking`, Homebrew tap instructions must use the explicit repository URL: `brew tap le0-VV/miniviking https://github.com/le0-VV/miniviking`. The shorthand `brew tap le0-VV/miniviking` makes Homebrew look for `le0-VV/homebrew-miniviking`.
  - The server verification CLI should be named `miniviking test`, not `miniviking smoke`.
  - Compatibility should be verified against a bone-stock, isolated OpenViking installation using real memory ingestion and retrieval workflows, with only OpenViking configuration pointed at Miniviking.
  - Stock OpenViking PyPI `0.1.12` was verified against Miniviking using an isolated Python 3.9 venv and only `OPENVIKING_CONFIG_FILE` pointed at Miniviking. A single local Markdown resource successfully ingested, generated semantic summaries, retrieved resources, ran session-context search, extracted one long-term memory, vectorized it, and retrieved it from `viking://user/memories`.
  - OpenViking `0.1.12` quirks observed during compatibility testing: published console scripts `openviking-server` and `openviking-viewer` point at missing modules; `add_resource` failed for a local directory with `Is a directory`; a single Markdown file is stored under a directory-like root where `glob("**/*.md", uri=root_uri)` returned no matches, but `ls(..., recursive=True)` exposed the readable Markdown leaf; broad `find(..., target_uri="viking://user")` returned resource matches, while `target_uri="viking://user/memories"` retrieved the extracted memory.
  - Codex sandbox localhost probes can report connection failures for Miniviking even when the host-side service is healthy. For local service verification, run Miniviking and endpoint probes outside the sandbox, and set `NO_PROXY=127.0.0.1,localhost,::1` because the OpenAI Python client may otherwise route local Miniviking requests through the user proxy.
  - Leonard's global default Python environment is `/Users/leonardw/.venvs/default/`; use it when a clean Python newer than the system Python is needed, including current OpenViking compatibility tests.
  - Low-RAM Llama compatibility finding: stock OpenViking `0.1.12` memory extraction prompts exceed a 2048-token prompt cap, so the Miniviking small tier needs at least a 4096 prompt/KV budget for out-of-box OpenViking compatibility.
  - Low-RAM Llama reliability finding after real OpenViking trials: resource ingestion, semantic summaries, embeddings, and resource retrieval work with `mlx-community/Llama-3.2-1B-Instruct-4bit` plus `embeddinggemma-300m-4bit`, but session memory extraction is not semantically reliable. It either copied OpenViking few-shot examples before prompt hardening, or returned zero/schema-invalid memories after prompt hardening. The 8 GB warning should remain strong.
  - Current OpenViking `0.3.14` compatibility finding: the package includes `openviking.server.bootstrap`, and `openviking-server` starts correctly under Leonard's default Python when dependencies are isolated. However, its v2 memory extractor sends about 5.5k estimated prompt tokens even for tiny sessions, so Miniviking's 4096 prompt/KV budget makes v2 fail and OpenViking falls back to a path that completes with zero extracted memories.
  - Low-RAM Llama 3B memory test finding: `mlx-community/Llama-3.2-3B-Instruct-4bit` with `embeddinggemma-300m-4bit` and an 8192 prompt/KV budget idled at about 1.9 GB physical footprint for the LLM worker, about 0.5-0.6 GB for the embedding worker, and about 18 MB for the server. A 7,149-token chat pushed the LLM worker to a 3.7 GB peak, and a 64-item embedding batch left the embedding worker at about 618 MB with a 1.0 GB recorded peak. It may fit on 8 GB Macs, but memory headroom is thin once macOS/OpenViking/browser activity is included, and structured memory extraction still needs reliability testing because one capped prompt copied the example placeholder.
  - Low-RAM non-Chinese candidate trial findings on May 14, 2026: `mlx-community/granite-3.3-2b-instruct-4bit` passed Miniviking selftest and returned valid JSON for a 7,005-token OpenViking-shaped prompt with a 3.0 GB LLM peak, but its schema was wrong and duplicated the same memory as nested objects; cache size was about 1.3 GB. `mlx-community/Phi-4-mini-instruct-4bit` passed selftest, returned the cleanest JSON/schema for the same prompt, and completed in about 30 seconds, but used about 4.1 GB LLM peak plus the embedding worker, making it too tight for an 8 GB default; cache size was about 2.0 GB. `mlx-community/Ministral-3-3B-Instruct-2512-4bit` loaded with `mlx-lm` but failed stock MiniViking chat/selftest because its tokenizer rejects `system` messages; with a temp user-only prompt adaptation it still failed JSON validation on the long prompt, used about 3.6 GB LLM peak, and cached at about 2.6 GB. Among these, Granite is the only plausible 8 GB non-Chinese default, but it needs schema repair/post-processing or stronger prompting; Phi is best quality for 12 GB+ or opt-in; Ministral should not be a low-RAM default.
  - Overnight prompt/refinement sweep findings on May 15, 2026: temp-only harnesses under `/private/tmp/miniviking_prompt_sweep.py`, `/private/tmp/miniviking_refinement_probe.py`, and `/private/tmp/miniviking_repeat_refine.py` tested Granite 2B, SmolLM3 3B 4-bit and 3-bit, Gemma 3 1B, Ministral 3B, StableLM 1.6B, SmolLM 1.7B, Hermes 3 Llama 3.2 3B, and Falcon3 1B. Only `embeddinggemma-300m-4bit` was left cached afterward.
  - SmolLM3 requires `enable_thinking=False` in the chat template, otherwise it emits thinking/prose instead of clean JSON. Even with no-thinking and an internal durability checklist, `mlx-community/SmolLM3-3B-4bit` only had clean passes on 3 of 6 focused repeat cases; it handled negative traps better than Granite/Hermes but missed explicit preferences, correction/latest-wins cases, and most multi-fact extraction.
  - Recursive/refinement loops did not solve low-parameter memory extraction. Candidate-classifier, self-refine, and model-visible filter passes often under-kept real facts, preserved transient facts, or introduced malformed/placeholder output. The best prompt shape was still a direct JSON-only durability prompt with a private checklist, plus host-side schema validation/repair for syntax only.
  - Focused repeat/refinement clean-case results: Granite 2B passed 1/6 cases cleanly and over-extracted transient/no-memory sessions; SmolLM3 3B 4-bit passed 3/6 cleanly but missed explicit preferences/corrections; Hermes 3B passed 2/6 cleanly and falsely saved time/thanks/Homebrew troubleshooting; Falcon3 1B passed 0/6 despite valid JSON. Gemma 3 1B, SmolLM3 3-bit, StableLM 1.6B, SmolLM 1.7B, and Ministral are not viable low-RAM defaults based on schema, context, tokenizer, or semantic reliability failures.
  - Current low-RAM LLM recommendation: no tested sub-3B/3B local MLX model is reliable enough to be the unattended 8 GB OpenViking memory-ingestion default. For 8 GB hosts, prefer embedding-only or a very strong API-provider recommendation; any local LLM should be opt-in/experimental with clear warnings and strict host-side schema validation.
  - Phi memory follow-up: installed `mlx-lm` 0.31.3 exposes memory-relevant generation knobs `max_kv_size`, `prefill_step_size`, `kv_bits`, `kv_group_size`, `quantized_kv_start`, and model load knobs `lazy=True` plus `model_config={"quantize_activations": ...}`. `mlx-community/Phi-4-mini-instruct-4bit` should be retested before ruling it out for 8 GB, because the previous about 4.1 GB LLM peak used a long OpenViking-shaped prompt path without KV cache quantization.
  - Phi aggressive memory retest finding on May 15, 2026: `mlx-community/Phi-4-mini-instruct-4bit` with `lazy=True`, `max_kv_size` 6144 or 8192, `prefill_step_size=512`, and no KV quantization loads at about 220 MB physical footprint but generation still peaks around 3.4 GB MLX memory and 4.0 GB process physical footprint on a 6,059-token OpenViking-shaped prompt. 4096 KV budget is not viable for stock OpenViking v2-sized prompts; it produced invalid repetitive text and was slower. KV quantization is not usable for Phi under `mlx-lm` 0.31.3 because generation fails with `RotatingKVCache Quantization NYI`, and activation quantization fails with `Mode ({m.mode}) does not support activation quantization`. Phi remains too memory-heavy and semantically unreliable for the unattended 8 GB default, but can remain an opt-in or 12 GB+ experimental candidate with strict JSON repair/schema validation and clear warning text.
  - Product decision on May 19, 2026: disable the local LLM by default on 8 GB machines; Miniviking should install/run embeddings only there unless the user explicitly opts into LLM mode.
  - Product decision on May 20, 2026: the 8-12 GB default tier should not use `mlx-community/Llama-3.2-1B-Instruct-4bit`; that model was intended for 8 GB machines and prior OpenViking memory extraction tests proved it is not reliable enough.
